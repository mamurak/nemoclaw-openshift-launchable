<Callout type="rh" title="Your gateway password (you'll need it to log in)">
The OpenClaw UI is password-protected. Log in with your gateway password — <strong><code>openshell-wad26</code></strong> by default, or whatever you set as <code>OPENCLAW_GATEWAY_PASSWORD</code>. Print yours any time:

```bash
grep OPENCLAW_GATEWAY_PASSWORD ~/nemoclaw-openshift-launchable/.env
```
</Callout>

Your agent's Control UI is running on port `30789` — but **inside the sealed sandbox's private network namespace**. The sandbox is network-sealed, so only `openshell forward` (which tunnels *through* the gateway + supervisor) can bridge into it.

## Expose the UI

Point `openshell forward` at your sandbox + the UI port:

```bash
openshell forward start 0.0.0.0:30789 shifty --background
openshell forward list
```

Confirm it's serving:

```bash
curl -s -o /dev/null -w "OpenClaw UI: HTTP %{http_code}\n" http://127.0.0.1:30789/
```

`HTTP 200` means the bridge is live: `openshell forward` → gateway → supervisor → the agent's UI.

<Callout type="note" title="Why not a Route like the gateway?">
The OpenShell <em>gateway</em> is a normal Service with an OpenShift Route. A <em>sandbox</em> is network-sealed — its listening port lives in a private namespace, so only <code>openshell forward</code> (which tunnels <em>through</em> the gateway + supervisor) can reach it. Stop it later with <code>openshell forward stop</code>; one forward per port.
</Callout>
