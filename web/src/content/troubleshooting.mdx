The gotchas we hit so you don't have to. Most are handled by the Helm chart — here's what to check if something's off (run the checks in the shell).

## Can't reach the agent UI on :30789
The agent UI is bridged out of the sealed sandbox by `openshell forward`. Check the forward and that the OpenClaw gateway is up inside the sandbox:

```bash
openshell forward list
openshell sandbox exec -n shifty -- sh -c 'tail -3 /sandbox/gateway.log'   # gateway listening?
```

## Can't reach the gateway
The gateway is exposed via an OpenShift Route. Check that the Route exists and the gateway pod is running:

```bash
oc -n openshell get route
oc -n openshell get pods
openshell gateway select cluster
openshell sandbox list
```

If the Route exists but the gateway isn't responding, check the pod logs:

```bash
oc -n openshell logs openshell-0
```

## Can't reach the OpenShift console
Check the console Route and pods:

```bash
oc -n openshift-console get route
oc -n openshift-console get pods
```

## OpenClaw asks for device pairing
That's expected — approve it (see **Part IV · Device Pairing**):

```bash
sbox-openclaw devices list
sbox-openclaw devices approve --latest
```

## Image pulls stall ("unexpected EOF")
Check the cluster's network connectivity — this is often an MTU or DNS issue on the underlying infrastructure.

<Callout type="note" title="Helm chart is re-deployable">
The Helm chart is idempotent — fix the cause and re-deploy to reconcile.
</Callout>
